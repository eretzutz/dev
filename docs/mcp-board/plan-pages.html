Plan pages from the mcp-board planner

Every plan in this repo is an HTML page like this one: the request kept at the top of the file, contents on the left, the essentials on the right, and diagrams that move. The mcp-board planner writes its plans only as JSON on the board, and nothing reminds it of the page. The plan is to write the convention down as rules a program can check, give the planner a starter page that already passes them, say it where Claude Code reads it every turn, and have document_plan warn about, or refuse, a plan that has no page.

The convention, as rules

“The format being used here” is the shape of shared-model-host.html, cf-tunnel.html and setup.html. berith’s docs/plan.html was written from the same request text. Each page started as a one-line request, and the request is still at the top of the file, followed by what was measured and decided. The markup differs from page to page, so the rules check features, not class names.

A chat-style page (an h1 and nothing else) fails E2, E3, E4, E5 and E6. The prototype was about 50 lines of regular expressions; P0 turns it into plandoc.mjs, with this folder’s pages as fixtures. The rules are a floor. They tell a page that follows the convention from one that does not; they do not judge whether the plan is any good.

The starter page

templates/plan.html is this page’s skeleton, taken from shared-model-host.html: the colour tokens for light, dark and print; the three-column shell that folds at 1240 px and 860 px; the scroll-spied contents and progress bar; the pause button. It has section stubs for Summary, Data flow, Process, Steps, Acceptance, Files and Open questions; right-panel cards for At a glance, Still to do and Diagram legend; and two diagram skeletons, each with one moving token. The tool fills in {{TITLE}}, {{BRIEF}}, {{DATE}} and {{LEDE}}. Untouched, it passes every rule except W8, which needs the real step titles.

Why the planner forgets

  • The role prompt says nothing about a page. PLANNER.md ends with “Always call the board tools; do not only write the plan in chat.” The page is never mentioned.
  • A prompt is read once. It reaches the model only when someone runs /mcp__board__planner. Claude Code does not send it again; after /compact it survives only as far as the summary keeps it.
  • Two projects never see the default prompt. MCP_BOARD_PROMPTS replaces the whole folder. xiliap reads docs/lessons/agents/board, berith reads docs/board, and neither mentions HTML.
  • Server instructions stay. Claude Code puts each server’s initialize instructions in the system prompt of every session that has the server; the session that wrote this page carries two such blocks. The board’s instructions are one sentence about get_board_summary today.
  • A tool description is read when it is needed. With many MCP tools, Claude Code defers their schemas and fetches one just before calling it, so document_plan’s description is read right before a plan is recorded.
  • The tool result has the last word. The model reads it right after acting. A reminder there is seen every time, and a refusal cannot be skipped.

What each session reads

The server’s instructions (system prompt, every session)

A shared board for planner, orchestrator and validator sessions. Call get_board_summary at the
start of a session and after every event; report through the tools, not only in chat.
Planner: every plan is also an HTML page, docs/<topic>/<slug>.html, in this project's
convention: the request verbatim in a leading comment, a left contents nav, a right
at-a-glance panel, animated data-flow and process diagrams. Start it with plan_doc_template,
check it with check_plan_doc, and pass its path as doc to document_plan. Prompt plan_doc has
the details. Orchestrator and validator: get_plan gives the page; read it.

document_plan’s description (read right before the call)

Planner: create or replace a structured implementation plan. Returns plan_id. Call this before any
implementation work. Replacing a plan keeps the status of every step whose id is unchanged.
Every plan has a page: pass doc, the path of its HTML page (plan_doc_template writes a starter;
check_plan_doc checks it). Without a passing page this tool warns, or refuses when the board
requires pages.

prompts/PLANNER.md, a new section

## Plan page
Every plan is also a page: docs/<topic>/<slug>.html, in this project's convention (prompt plan_doc).
1. plan_doc_template {path, title, brief}. The brief starts with the request, word for word.
2. Fill it in: summary, data flow and process diagrams, steps, acceptance, files, open questions.
   The board's steps are the page's steps, with the same titles.
3. check_plan_doc {path} until it has no errors.
4. document_plan {..., doc: path}.
On the next iteration, edit the same page first (a dated UPDATE line in the brief), then
document_plan {plan_id, ...}. When a plan is done, write what was verified into its page.

VALIDATOR.md gains one rule: “check_plan_doc {plan_id}; an E error fails validation, and the page’s status tags must match what you found.” ORCHESTRATOR.md gains one: “get_plan gives doc; read the page before you start. Don’t edit it: put what it should say in report_progress evidence.”

get_board_summary gains docs_root and plan_doc_mode at the top, and each plan gains page: {path, status, changed, errors, warnings}, checked as it is now, where status is one of ok, missing, failing or behind, and changed says it was edited since document_plan checked it. get_plan returns the same page; list_plans shows doc and the status. built this way The plan called the live view doc, the same name as the stored record; it is page so the two don’t collide.

Compatibility and risks

  • xiliap and berith keep working. With warn as the default, their document_plan calls still succeed; the results gain a plan_doc field. Their hooks are not asked about document_plan, today or after.
  • berith plans in batches. just board-plan D10 makes a plan from a stretch of docs/handoff.md, while its one page, docs/plan.html, covers the whole app. Pointing every batch at that page passes E1–E6 but trips W8. How batches map to pages is berith’s choice.
  • Regular expressions, not a DOM. A page can satisfy the rules and still be thin (an empty <nav> with three links passes E3). The check is a floor; the validator still reads the page.
  • The server writes one kind of file. plan_doc_template creates new .html files under the docs root and nothing else. It never overwrites.
  • Reads touch the pages. get_board_summary hashes each active plan’s page. The pages here are 50–230 KB, a few milliseconds each. It still never writes the board.
  • Instruction length. Server instructions share the system prompt with every other server’s. Five sentences is the budget.
  • The template copies this repo’s CSS. If the convention changes, templates/plan.html and PLAN_DOC.md change with it, and the fixtures catch a rule that no longer fits.
