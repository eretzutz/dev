Hosting oMLX beyond the Mac

oMLX on the Mac Studio answers only on 127.0.0.1:8000. It is now served to your own devices over the tailnet with Tailscale Serve: no public surface, no change to how oMLX runs. The original ask — a public https://omlx.xilia.net through a Cloudflare Tunnel, with a small Rust gate in front of oMLX — is planned in full below and deferred until something outside the tailnet needs the API.

Plan Planned 20 Nov 2026 from the stub in this file decided 20 Nov 2026 · Tailscale Serve · live Cloudflare tunnel · deferred, nothing installed

The route taken: Tailscale Serve

Live since 20 Nov 2026. One command turned it on, one turns it off, and oMLX was not touched.

ThingAs it is now
Base URL for clientshttp://steves-mac-studio.tail059551.ts.net:8000/v1, the short form http://steves-mac-studio:8000/v1, or by tailnet address http://100.72.79.31:8000/v1, which needs no name resolution. Same port as on the Mac itself; only the host differs.
Who can reach itDevices on your tailnet: one user, five machines. Funnel is off, there is no DNS record and no open port, so nothing on the public internet can.
Forwardingtailscaled (Homebrew 1.104.7, a boot-time daemon) forwards tailnet TCP port 8000 to 127.0.0.1:8000. A plain TCP forward, not Serve’s HTTP proxy: the proxy answers only for the Mac’s tailnet name and returned 404 to a request addressed to the tailnet IP. The config is stored by tailscaled and survives restarts.
EncryptionWireGuard, device to device. The URL is http because the tailnet does not have HTTPS certificates enabled; the traffic between devices is encrypted either way (open question on switching to https).
oMLXUnchanged: still bound to 127.0.0.1:8000, still the launchd agent sh.brew.omlx, still requires a key. The dashboard is at /admin on the same URL.

Tooling

In this folder. just is the front end; Python is one stdlib script that runs on the system python3 (3.9); Rust is not involved on this route — the gate belongs to the deferred public hostname. 

just up       # tailscale serve --bg --tcp=8000 tcp://127.0.0.1:8000, after the origin guard
just down     # tailscale serve --tcp=8000 off; oMLX keeps running locally
just status   # the serve config and what listens on the origin port
just check    # scripts/check.py: every check below, exit 1 on any failure
just url      # the base URLs to give a client: by name, short, and by tailnet IP

scripts/check.py tests behaviour, not settings: a request with no key must get 401 from the origin and from the tailnet URL, by name and by IP; the serve config must be a TCP forward of port 8000 to the origin; Funnel must be off; oMLX must listen on loopback only. It then reads the settings to explain any failure, lists sub keys by fingerprint, and warns about sleep. just up runs the origin half first and refuses to serve if oMLX would answer without a key.

Verified 20 Nov 2026 from the Mac itself, by full name, short name and tailnet IP: /v1/models with no key 401, /health 200, Funnel off, origin listener still 127.0.0.1:8000. Both online peers (apple-m4-pro, stephens-mac-mini) answer a Tailscale ping directly. The guard was also run against a stand-in origin that answers without a key and against a dead port; it failed both, as it should. From a second device the same day (the MacBook Pro, tailnet node apple-m4-pro): by tailnet IP, 401 API key required from oMLX, and the request is in oMLX’s log — hosting works end to end. By short name: Could not resolve host, although Tailscale DNS reports enabled on that laptop — a name-resolution problem there, still open (see below). With a real key, Claude Code and opencode both completed a prompt through the tailnet IP (connecting an agent); that run was from this Mac, not yet from the MacBook.

If a device cannot resolve the name

Could not resolve host is decided on the calling device before anything is sent, so it says nothing about this Mac. On that device, in order: 

tailscale status | head -1      # is Tailscale connected here, and which tailnet node is this device?
curl -i http://100.72.79.31:8000/v1/models
                                # by tailnet IP, no DNS involved: a 401 means the path works and only names are broken
tailscale dns status | head -4  # "Tailscale DNS: enabled"? if not: tailscale set --accept-dns=true,
                                # or tick "Use Tailscale DNS settings" in the menu-bar app

Until names resolve there, a client on that device can simply use http://100.72.79.31:8000/v1. The address is stable for as long as this Mac stays in the tailnet.

Still to do, by you

  • Mint a sub key for the MacBook in the oMLX dashboard, 32 characters or more (how), and one for each other device. Until then a remote device would have to carry the main key, which is also the admin credential. just check warns while there are none.
  • Set the agents up on the MacBook with that key: source clients/claude-omlx.sh, copy clients/opencode.json. It reaches the server by tailnet IP today; its name lookup is still to sort out, or to sidestep with the IP.
  • Decide the power settings. System sleep is set to 1 minute and is held off only by caffeinate assertions. When the Mac sleeps, the URL stops answering.

Limits to know

  • The loopback caveats below still apply, to a small audience. tailscaled connects to oMLX over loopback, so oMLX’s wrong-key lockout does not apply to tailnet devices, and if skip_api_key_verification were switched on, every tailnet device would get inference and the dashboard with no key. With five devices that are all yours this is acceptable; just check is how you confirm it has not changed. If the tailnet ever gains other users, restrict who may reach this Mac’s port 8000 in the tailnet access rules first.
  • After a reboot the URL answers 502 until you log in. tailscaled starts at boot; oMLX is a login agent.
  • The whole server is served, dashboard included. That is deliberate here: it is how you administer oMLX from another device.
  • To undo: just down. Nothing else was changed.

Claude Code

CLAUDE_CODE_AUTO_COMPACT_WINDOW=262144          # and compaction measured against it
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1      # no telemetry or background calls to Anthropic

claude --settings '{"useAutoModeDuringPlan":false}' --disallowedTools LSP "$@"

Two lines Claude Code prints on start are expected here: a notice that claude.ai connectors are disabled because another auth source is set, and unrecognized_model for the local model’s name. The two flags on the last line are oMLX’s defaults for a local model: planning asks for approval instead of using a classifier that can time out during a long prompt read, and the LSP tool is off because its schema arriving mid-session would make the server re-read the whole conversation.

What forwarding changes

Anything on the Mac that forwards outside traffic to oMLX — tailscaled today, cloudflared in the deferred plan — connects to it over loopback. From oMLX’s side, a request from anywhere has the peer address 127.0.0.1. Four things in oMLX 0.8.0 depend on that address or on the bind being loopback. Paths are relative to the package directory above. With a tailnet of your own devices these are caveats; with a public hostname they are the reason for the gate.

1. The wrong-key lockout does not apply to loopback peers

admin/auth.py:263–289. _client_key() returns None for a loopback peer, and check_api_key() then verifies with no failure budget (“Clients on this machine are not limited”). The budget is otherwise 8 wrong keys, then a 30 s lockout, then 300 s. Through a tunnel, key guessing is unlimited.

2. One setting removes authentication on a loopback bind

server.py:393–407 and admin/auth.py:386–420. With skip_api_key_verification on and a loopback bind, both inference and the whole admin API accept requests with no key; the same is true if the key is removed. The reasoning is “loopback bind means local callers only”, and a tunnel keeps the loopback bind while making the callers public. The setting is off today. It is a dashboard toggle, so the plan must not depend on it staying off.

3. Several routes answer without a key

PathWithout a key, on loopback and on the tailnet todayOn a public hostname
/admin200, the login page (about a hundred admin routes sit behind it)not published tailnet only
/docs, /openapi.json200, the full route listnot published
/health200not published
/api/status401not published
/v1/models401published

4. /v1/ is not all inference

A sub key also reaches /v1/mcp/execute (run an MCP tool on this Mac), /v1/web/fetch (the server fetches a URL for you), /v1/models/{id}/load and /unload, and the audio and realtime routes. A filter of “anything under /v1/” would publish all of them. Separately, the only length rule for a key is four characters (admin/auth.py:328–359), so key strength is ours to enforce.

None of this is a bug in oMLX. These are sensible defaults for a server that binds loopback. They stop being true the moment a local process forwards the internet to it — and that applies equally to tailscale serve, an SSH forward, or any reverse proxy on the Mac, not only to Cloudflare.

Deferred: the public hostname

Everything from here to Files is the plan for https://omlx.xilia.net through a Cloudflare Tunnel. None of it has been built or installed. It is kept because the research is done and the design holds; build it when a caller that cannot join the tailnet needs the API. The order does not change: the gate first, on loopback, then the tunnel.

What already exists carries over. The justfile here grows the tunnel recipes rather than being replaced, and scripts/check.py is the origin half of what the plan below calls preflight.py.

Decisions

#DecisionWhy
D1Cloudflare Tunnel, named omlx, locally managed: a credentials JSON and a config file on the MacThe zone is already on Cloudflare, so the hostname costs nothing and needs no new account. Locally managed matches atuin-host, keeps the ingress rules in a reviewable file, and lets cloudflared tunnel ingress validate test them offline. The dashboard-managed kind keeps the rules in the dashboard instead.
D2oMLX is not reconfigured: same bind, same port, same launchd job. The only change to its settings is adding sub keys.Local use (omlx launch …, the dashboard) keeps working exactly as now, and taking the tunnel down returns the Mac to today’s state.
D3omlx-gate sits between cloudflared and oMLX on 127.0.0.1:8100; cloudflared never points at :8000Findings 1–4. The policy that matters has to run on the Mac, in code we own, and must not depend on a setting in someone else’s dashboard.
D4The gate’s allowlist is method + exact path, default deny, in gate.toml. The two outer layers (cloudflared ingress, edge rule) use one coarse rule: ^/v1/One precise list in one place. The outer layers only shed obvious noise (/admin, /.env, scanners) before it reaches the Mac, so they cannot drift out of sync with the list.
D5Remote clients get oMLX sub keys: one per client, named, at least 32 random characters. The main key never leaves the Mac. The gate stores no keys.The main key is the admin credential; sub keys are inference-only by oMLX’s own rule. One key per client makes a leak a one-row revocation. oMLX stays the only key store.
D6The gate restores the lockout, keyed on CF-Connecting-IP, with oMLX’s own numbers (8 wrong keys, 30 s, then 300 s)Finding 1. The gate sees the upstream 401s and the real client address; oMLX sees neither usefully. The header is trustworthy here because the gate’s only client is cloudflared on loopback.
D7A canary: every 15 s the gate sends oMLX a request with no key and expects 401. Anything else and the gate answers 503 to everyone until it is 401 again.Finding 2. It tests behaviour, not a settings file, so it also catches a removed key, a future default change, or a setting this plan does not know about.
D8The admin dashboard is never on the public hostname. Remote admin goes over Tailscale.It can download models, change settings and holds upload tokens. Your devices are already on the tailnet.
D9Remote clients stream. Non-streaming requests are allowed but bounded by the edge’s idle limit.The edge gives up on a response after roughly 100–120 s with no bytes (error 524). sse_keepalive_mode: chunk, already set, sends keep-alive chunks while the model reads a long prompt. A non-streaming request sends nothing until it is finished.
D10Gate and tunnel run as launchd agents in the user session, not boot-time daemonsoMLX is an agent and only exists after login. A tunnel that comes up at boot would front an origin that is not there.
D11cloudflared’s files get their own names: ~/.cloudflared/xilia.net.pem for the login certificate, omlx.yml for the configA login certificate is scoped to one zone. If a certificate for another zone is in the default place (the Atuin tunnel is on withcreo.ai), tunnel route dns creates the record in that zone. Separate names let both tunnels share a machine.
D12Edge rules are scoped with http.host eq "omlx.xilia.net" and applied read-modify-writeThe zone serves a live site. A rule without the host clause, or an API call that replaces a ruleset, would change that site’s behaviour.
D13The tooling lives beside this file, in docs/omlx/The repo’s one precedent (docs/git/justfile) keeps a topic’s tooling in its folder. A separate repo like atuin-host is the alternative (open question).

Data flow

Process

Tooling: Rust, Python, just

The split is the usual one. Rust is the part that sits in the request path and must stream without buffering. Python is stdlib-only scripts that check and render, one job each, runnable on the Mac’s own python3 (3.9.6: no tomllib, no match). just is the only thing you type.

Rust — omlx-gate

One crate, one binary, edition 2024 like mcp-conventions. tokio, hyper and hyper-util for a streaming server and client, serde + toml, clap, tracing. No TLS code at all: both sides are loopback. Three subcommands:

  • omlx-gate serve --config gate.toml — the proxy on :8100, plus /ready on a second loopback port (:8101) that the tunnel never forwards to
  • omlx-gate check --config gate.toml — parse the config and print the effective route table
  • omlx-gate drift --config gate.toml — read oMLX’s /openapi.json, classify every route as allowed, denied, or unclassified, and exit 1 if any is unclassified. Run it after every brew upgrade omlx.
# docs/omlx/gate.toml — the whole public surface, in one reviewable file
listen   = "127.0.0.1:8100"
ops      = "127.0.0.1:8101"
upstream = "http://127.0.0.1:8000"

[allow]   # method + exact path; {x} matches one segment; everything else is 404
routes = [
  "GET    /v1/models",
  "POST   /v1/chat/completions",
  "POST   /v1/completions",
  "POST   /v1/responses",
  "GET    /v1/responses/{id}",
  "DELETE /v1/responses/{id}",
  "POST   /v1/messages",
  "POST   /v1/messages/count_tokens",
  "POST   /v1/embeddings",
  "POST   /v1/rerank",
]

[deny]    # known upstream routes we chose not to publish; lets `drift` tell "decided" from "new"
prefixes = ["/admin", "/api", "/docs", "/redoc", "/openapi.json", "/health", "/cluster",
            "/tokenize", "/detokenize", "/v1/tokenize", "/v1/detokenize",
            "/v1/mcp", "/v1/web", "/v1/audio", "/v1/realtime",
            "/v1/models/", "/v1/decisions", "/v1/systemone"]

[limits]
max_in_flight      = 4       # oMLX's own cap is 8; half stays free for local use
max_body           = "32MB"
wrong_key_budget   = 8       # oMLX's numbers for non-loopback peers
first_lockout_s    = 30
repeat_lockout_s   = 300
client_key         = "CF-Connecting-IP"   # IPv6 clients are bucketed by /64

[canary]
interval_s = 15
request    = "GET /v1/models"   # sent with no key; any status but 401 closes the gate

The policy is one pure function, so the table of cases is the test:

// gate/src/policy.rs
pub enum Verdict {
    Forward,                         // stream both ways, count a 401 from upstream
    NotFound,                        // not on the allowlist            -> 404
    NoCredential,                    // no Bearer and no x-api-key      -> 401
    LockedOut { retry_after: u64 },  // wrong-key budget spent          -> 429
    Busy { retry_after: u64 },       // max_in_flight reached           -> 429
    OriginOpen,                      // canary saw a keyless non-401    -> 503
    OriginDown,                      // connect refused                 -> 503
}
pub fn decide(req: &RequestMeta, state: &GateState, cfg: &Config) -> Verdict

The access log is one JSON line per request to ~/Library/Logs/omlx-tunnel/gate.log: time, cf-ray, client address and country, method, path, status, a key fingerprint (first 8 hex of its SHA-256, never the key), bytes, time to first byte, duration. Never a body: prompts are private.

Not in the first version: OPTIONS (browser callers are not a target, and a key in a web page is a leaked key) and WebSocket upgrades (the realtime routes authenticate in-band, where the gate cannot count failures). Both are in P5.

#                                  prints time to first chunk and the longest gap
#  6  POST /v1/messages with x-api-key -> 200 (the Anthropic-shaped route and header)
#  --slow: a long-prompt stream (keep-alive chunks must carry it through prefill), and a
#          long non-streaming request to record where this zone's idle limit actually is

python3 scripts/edge.py plan|apply            # P4: host-scoped edge rules; plan is the default

P0 Posture and keys — no Cloudflare yet partly done

Done 20 Nov 2026: Tailscale Serve is live on tailnet port 8000 (the route taken), with the justfile and the origin checks. Two deviations from the sketch below: the script is scripts/check.py, not preflight.py, and Serve is a TCP forward of port 8000 carrying plain http, because the tailnet has no HTTPS certificates enabled and the forward also answers by tailnet IP. Not done: sub keys, the power decision.

  • scripts/preflight.py, origin checks only, and the justfile skeleton with check-deps and preflight.
  • Mint sub keys in the oMLX dashboard, on the Mac: one per remote client, plus one named smoke. just key-new prints a 43-character URL-safe random key to paste in. The main key is not handed to any remote client.
  • Private access for your own devices: Tailscale Serve puts oMLX, dashboard included, at the Mac’s ts.net name for the tailnet only. This is also the remote-admin path for good (D8). The loopback caveats in the findings apply here too, to an audience of your own five machines.
  • Decide the power settings (open question); preflight warns until system sleep is off.

Done when: just preflight origin is green, and the smoke sub key lists models on 127.0.0.1:8000.

P1 The gate — Rust, loopback only

  • The omlx-gate crate: config, decide(), the streaming proxy, the lockout table, the canary task, the access log, and the three subcommands.
  • gate.toml as above, with every route in today’s /openapi.json classified, so gate-drift starts green.
  • scripts/render.py for the gate’s plist; the agent net.xilia.omlx-gate with RunAtLoad and KeepAlive.

Done when: cargo test is green; through 127.0.0.1:8100, /admin is 404, a keyless call is 401, nine wrong keys from one faked CF-Connecting-IP end in 429, and a streamed completion shows the same chunk cadence as a direct call. And the drill: turn skip_api_key_verification on in the dashboard, watch the gate answer 503 within one canary interval, turn it off, watch it recover.

P2 The tunnel

  • just tunnel-install (brew install cloudflared), tunnel-login (the browser step: choose xilia.net; the recipe then moves the certificate to its own name and refuses to run if an unknown cert.pem is already there), tunnel-create, tunnel-route.
  • tunnel-route fails unless the record it created is exactly omlx.xilia.net. A certificate for the wrong zone produces a record under that zone instead, and that must be loud.
  • render writes omlx.yml and the tunnel plist (cloudflared tunnel --config …/omlx.yml --no-autoupdate run; Homebrew owns upgrades). ingress-check runs ingress validate and the ingress rule table.
  • just up, down, status, logs.

Done when: just status shows the tunnel’s edge connections, and from another network curl -i https://omlx.xilia.net/v1/models returns 401 with a cf-ray header, and /admin returns 404.

P3 Proof from outside, and the clients

  • scripts/smoke.py and just smoke; then just smoke-slow once, and write the two measured numbers into this file: time to first chunk for a long prompt, and where the idle limit cut the non-streaming request.
  • Point the clients at it. Any OpenAI-compatible client: base URL https://omlx.xilia.net/v1, the client’s own sub key as the API key. Anthropic-shaped clients: base URL https://omlx.xilia.net; oMLX accepts the key as a Bearer token or as x-api-key. omlx launch stays the local path.
  • A README.md runbook: up, down, status, logs, revoke a key, what each failure code means.
  • The reboot drill: restart, log in, do nothing, run just status and just smoke.

Done when: just smoke is green from outside the LAN, one real client works end to end, and the reboot drill needed no hands after login.

P4 Edge rules recommended

The gate already enforces everything; these two rules shed noise before it uses the tunnel or wakes the Mac’s logs. 

# custom rule — Block
(http.host eq "omlx.xilia.net" and not starts_with(http.request.uri.path, "/v1/"))

# rate limiting rule — count by IP, 10 s period, block
(http.host eq "omlx.xilia.net")

scripts/edge.py plan first reads the zone’s plan and its existing rules and prints what it would add. The free plan has one rate-limiting rule for the whole zone; if the site already uses it, this plan does not take it and the gate’s lockout stands alone. apply adds or updates only rules it created, matched by a fixed ref, and never replaces a ruleset (D12). Needs CLOUDFLARE_API_TOKEN in .env, scoped to WAF edit and zone read on xilia.net. The same two rules can be clicked in the dashboard instead.

Done when: curl https://omlx.xilia.net/admin is refused by Cloudflare (no gate log line), and the site at the apex behaves exactly as before.

P5 Later, only if something asks for it

  • Cloudflare Access with a service token. A second credential, checked at the edge (CF-Access-Client-Id and CF-Access-Client-Secret headers, a Service Auth policy). Worth it only if every client can send two extra headers; many chat tools cannot.
  • Audio and realtime. Needs WebSocket pass-through in the gate and a way to bound in-band auth failures.
  • Usage and quotas per key. The gate log already has fingerprints, sizes and durations; a small scripts/usage.py would summarise it. Hard quotas would be a new [limits] table.
  • An edge gateway. Cloudflare AI Gateway or a Rust Worker on the route, for caching, analytics or edge-side quotas. An addition in front of the gate, not a replacement for it.

Within Cloudflare

  • Dashboard-managed tunnel (a token instead of a config file). Works equally well; rejected only because the ingress rules would live in the dashboard rather than in this repo (D1).
  • Quick tunnel (trycloudflare.com). A random hostname and no account; useful for a five-minute demo, not for omlx.xilia.net.
  • Access in front of everything. Strong, but it needs clients that can send extra headers or follow a browser login. Kept as P5.
  • A Rust Worker as the gate. Tempting, given the Worker tooling already on this machine. Rejected as the only gate because the check that matters — is the origin still demanding a key — has to be made from where the origin is. Possible later, in front of the local gate.

Risks and mitigations

For the deferred public hostname. The limits of the tailnet route are listed in its own section.

RiskMitigation
oMLX stops demanding a key: the skip setting is switched on, the key is removed, or an upgrade changes a default.The canary closes the gate within 15 s and keeps it closed (D7). preflight refuses up. Neither reads oMLX’s intent; both test its behaviour.
An oMLX upgrade adds, renames or moves a route.Default deny: a new route is private until someone adds it to gate.toml. gate-drift makes the new route visible; a renamed allowed route shows up as a 404 in smoke.
A sub key leaks.One key per client (D5), so revocation is deleting one named row in the dashboard. The gate log shows which fingerprint was used, from where.
A valid key is used to saturate the GPU.max_in_flight in the gate, below oMLX’s own cap, so local use keeps headroom. Per-key caps are a P5 item.
A long prompt or a non-streaming request hits the edge’s idle limit (524).Keep-alive chunks are already on; remote clients stream (D9). smoke-slow records the real limit on this zone, and the number goes in the runbook.
The Mac sleeps, loses power, or is logged out.The power decision in the open questions; preflight warns. While down, the edge answers 530 quickly, so clients fail fast and can retry.
An edge rule changes the live site on the same zone.Every expression carries the host clause; edge.py defaults to plan, touches only rules it created, and never replaces a ruleset (D12). P4’s exit check includes the site.
The login certificate belongs to another zone and the DNS record lands there.A certificate file of its own (D11); tunnel-login refuses an unknown cert.pem; tunnel-route checks the record’s exact name.
Zone-level bot protection challenges API clients, which cannot solve a challenge.smoke runs from a plain HTTP client, so a challenge shows up as a failed check on day one. The fix is a host-scoped exception, handled in P4.
A bug in the gate: an outage, or a hole.Small code with one pure policy function and a table test that includes path tricks. The outer ^/v1/ rules do not depend on it, so /admin stays unreachable even if the gate’s list were wrong.
Cloudflare can read prompts and completions.Accepted for this use, and stated in the runbook. If that changes, the VM row with TLS passed through to the Mac removes the reader.
Homebrew upgrades cloudflared or oMLX under a running agent.KeepAlive restarts them. just status prints both versions; the after-upgrade routine is gate-drift, then smoke.

Open questions

  • Answered 20 Nov 2026: who calls this from outside the tailnet? Nobody yet, so the route is Tailscale Serve and the tunnel waits.
  • Power. May the setup change pmset (system sleep off, restart after power failure on)? And after a reboot, is logging in by hand acceptable, or should the Mac log in automatically? Automatic login cannot be combined with FileVault. Recommendation: sleep off and auto-restart on; keep manual login. This matters for the tailnet route as much as for the tunnel.
  • https on the tailnet? It needs HTTPS certificates switched on for the tailnet in the Tailscale admin console, which is yours to do and puts the machine name steves-mac-studio.tail059551.ts.net in the public certificate-transparency logs for good. The traffic is already encrypted by WireGuard, so the gain is a URL without a port and clients or browser features that insist on https. Recommendation: stay on http until a client refuses it; the change is then one console switch and one edit to the up recipe.
  • Where the tooling lives. It is here in docs/omlx/ now. Its own repo beside atuin-host only makes sense if the tunnel and the gate get built.
  • The main key. It is 20 characters. Once each device has its own sub key the main key never travels, so rotating it is optional.
  • Deferred with the tunnel: the zone’s plan and whether its single rate-limiting rule is free (edge.py plan answers it); and whether any remote client needs more than text inference — audio, realtime, MCP tools and web fetch are denied by default in gate.toml, and MCP tool execution deserves its own decision.
