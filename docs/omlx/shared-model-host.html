One oMLX server for every user of this Mac

Three people were running oMLX on the Mac Studio at once: your server on 127.0.0.1:8000, phil’s on :8002 and nate’s on :8003. Every oMLX server loads each model it serves into its own memory, so three servers can hold three copies of the same model in the Mac’s 96 GiB. The plan is to run one server, start it at boot as a system daemon owned by your account, and give every user a key of their own for http://127.0.0.1:8000/v1. The models folder does not move.

Decided 20 Nov 2026: one server for everybody, not a shared models folder. A shared folder saves disk space, but every server would still keep its own copy of each model in memory, and memory is what runs out on this Mac. One server keeps one copy, shares the prompt cache, and lets the scheduler and memory guard see all the load. Everyone else connects over loopback with a key of their own.

Why one server, not one folder

This is an example, not a measurement: phil and you both on the 27B model, nate on gemma. The bars show weights only, using on-disk sizes; the KV cache comes on top.

Another reason: your home folder is drwxr-x---, so other users cannot read your model files. That is why someone would think of a shared folder. With one server running as you, they never need to read the files.

Doing it

You, once

  1. Install the daemon. It asks for your password once. When it finishes, it runs just check, and the host line should read “oMLX is the system daemon local.omlx, running as steve”. 
    cd ~/dev/eretzutz/dev/docs/omlx
just daemon-install
  2. Prove it still gets the GPU. MLX runs on Metal. A daemon is a different launch context from a login agent, so complete one real prompt before you rely on it: 
    just key-add steve-test
export OMLX_KEY='<the key it printed>'
curl -s http://127.0.0.1:8000/v1/chat/completions \
  -H "Authorization: Bearer $OMLX_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"Qwen3.8-27B-oQ4e-mtp","messages":[{"role":"user","content":"say hi"}],"max_tokens":16}'
tail -n 40 /opt/homebrew/var/log/omlx.log   # look for Metal errors
just key-rm steve-test
    If it fails, just daemon-uninstall puts the login agent back exactly as it was.
  3. Mint a key for each other user, and pass it on privately. It is shown once. 
    just key-add phil
just key-add nate
  4. Remove the leftover folder from the first attempt. It is empty and owned by root: 
    sudo rmdir /Users/Shared/omlx/models /Users/Shared/omlx

Each other user

In their own login, for example phil:

  1. Point their tools at your server with their key: 
    export OMLX_KEY='<phil’s key>'
# any OpenAI-compatible client
base URL   http://127.0.0.1:8000/v1
# Claude Code: needs its own copy of clients/claude-omlx.sh (steve’s home is not readable)
OMLX_HOST=127.0.0.1 claude-omlx
  2. Stop their own server. In their oMLX.app, stop the server and turn off starting it at launch (server.auto_start_on_launch in their ~/.omlx/settings.json). Or quit the app and remove it from Login Items. Once they have switched, they can delete any models in their own ~/.omlx/models. We could not see what is there, because their homes are private too.
  3. New models come from you, through the dashboard. Downloading a model is an admin action, and sub keys cannot use the admin API.

Afterwards, just check stops printing “phil runs another oMLX server”.

Tooling: just, Python, Rust

This folder already had just as the front end and a stdlib Python script for checks, both running on the system python3 (3.9). This plan adds one more script. Rust is not needed: nothing here sits in the request path. oMLX already checks keys, and omlx-gate in cf-tunnel.html is still needed only for a public hostname.

RecipeWhat it does
just daemon-installRenders the plist as you, runs brew services stop omlx, installs /Library/LaunchDaemons/local.omlx.plist (root:wheel 0644), bootstraps it into the system domain, waits until the daemon’s own pid listens on 127.0.0.1:8000 and /health answers, then runs the origin guard. If the guard fails, it runs just down.
just daemon-restartlaunchctl kickstart -k system/local.omlx, then the same wait and guard. Run it after brew upgrade omlx, because brew restarts only the jobs it manages.
just daemon-uninstallBoots the daemon out, deletes its plist, runs brew services start omlx, then waits and runs the guard. This is the undo.
just key-add NAMEGenerates a 43-character key and creates it through oMLX’s admin API with the main key. The running server stays the only writer of settings.json. Prints the key once and refuses a name that already has a key.
just key-list / key-rm NAMELists keys by name, fingerprint and date, never the key itself. Revokes by name.
just checkThe existing posture checks, plus host (which launchd job answers on the origin, run as whom, with which settings) and servers (every other oMLX server on the Mac, for any user).
just status / urlNow also show the launchd job and the on-Mac URL.

scripts/host.py holds the plist, wait and key logic. It imports its helpers from scripts/check.py, so both use the same settings path, which they resolve the way oMLX does: OMLX_BASE_PATH, then the app’s bootstrap file, then ~/.omlx. The plist starts from Homebrew’s keg plist, so the program path and PATH follow the formula. Everything that decides who oMLX runs as is set explicitly: UserName, HOME, USER, and OMLX_BASE_PATH. The rendered plist has no LimitLoadToSessionType, which applies only to agents. The label is not sh.brew.omlx, because brew services would treat a job with that label as its own.

The plist is rendered for your account on purpose. If host.py plist is run as root, it refuses. It also refuses to render a plist for settings that have no main key or have key checks turned off. That way the daemon cannot be made to start a keyless server at boot.

Why not sudo brew services start --sudo-service-user steve omlx? Homebrew 7.0.15 does support it, and it sets UserName, but it sets neither HOME nor OMLX_BASE_PATH. That would leave the settings path to launchd’s defaults, and the settings path is the one thing that must not be wrong here.

What is verified

Verified 20 Nov 2026, on the Mac Studio, without sudo:

  • just check passes. The new host line reports the login agent (pid 81077) and the reboot gap. The servers lines name phil (pid 1290, 127.0.0.1:8002) and nate (pid 6507, 127.0.0.1:8003).
  • host.py plist renders a plist that passes plutil -lint, with UserName steve, HOME /Users/steve and OMLX_BASE_PATH /Users/steve/.omlx.
  • A full key round trip on the live server. key-add created a 43-character key. With it, /v1/models returned 200 and listed the three models. The admin API returned 401 for it. A second key with the same name was refused. After key-rm, the key got 401. Afterwards settings.json was intact: same size, still mode 600, no keys left behind.
  • host.py wait reports the running agent at once, and fails on a job that does not exist. It works under just too.
  • One quirk found along the way. When started by just, netstat lists no TCP sockets at all (Darwin 27.2, just 1.59), so under just check the other servers appear without their ports. They are found by process title. The origin’s own process is found with lsof, which is not affected. A simulated netstat failure was also tested: it produces no false FAIL.

Not yet verified, because it needs your password: daemon-install itself, the GPU under the daemon (step 2 above), a reboot with someone other than you logging in first, and phil and nate switching over.

What the first attempt got wrong

This is kept here so nobody brings these steps back. Each one was checked against oMLX 0.8.0’s source or the Mac itself.

StepWhat actually happens
just config-shared: set "model_path" in ~/.omlx/settings.jsonno effect oMLX reads the model folder from model.model_dirs (settings.py), OMLX_MODEL_DIR, or --model-dir. A top-level model_path is ignored, and it is dropped the next time oMLX saves its settings. The recipe also rewrote the file holding the API key in place, with no restart afterwards. Removed.
Copy the Homebrew plist into /Library/LaunchDaemonsopens the tailnet With no UserName, oMLX runs as root and reads /var/root/.omlx/settings.json, which has no key. With no key on a loopback bind, oMLX accepts every request (server.py, verify_api_key). tailscale serve was already forwarding, and just up’s guard would not run again. The login agent would also have stayed loaded, so two jobs would have competed for one port. The source path /Users/steve/.launchd/ does not exist, and launchctl load is deprecated.
sudo chown -R staff:staff /Users/Shared/omlx, chmod -R 775wrong There is no user named staff. A recursive 775 would mark every weight file executable. The folder that exists is root:staff 775 and empty. With one server, it is not needed at all.
“Run just check to prove it”proves nothing here At the time, check tested only the key and tailnet posture, none of the shared setup. It now also checks the launchd job and the other servers.

Limits and risks

  • One queue. Everyone shares max_concurrent_requests: 8 and the memory guard, so one user’s long prefill can slow down another user’s reply. That is the trade for not holding duplicate weights.
  • Everything the server does, it does as you. Inference does not touch files, but MCP tools would: they would run with your file access on behalf of any key holder. No MCP config is set today (mcp.config_path: null). Decide before you add one.
  • Every local user is a loopback peer. oMLX’s wrong-key lockout does not apply to them. If skip_api_key_verification were ever turned on, every user of this Mac and every tailnet device would get inference and the dashboard with no key. just check fails if that happens, and host.py plist refuses to render.
  • FileVault is on. After a reboot nothing runs until someone unlocks the disk at the login window. After that, the daemon starts no matter who unlocked it.
  • Sleep. A daemon does not keep the Mac awake. System sleep is still 1 minute, held off only by assertions; that is the open question in cf-tunnel.html.
  • Upgrades. After brew upgrade omlx, the old version keeps serving until just daemon-restart.
  • Your own oMLX.app is also running. If it ever starts a server of its own on port 8000, the daemon cannot bind the port. just check reports this as “the system daemon local.omlx is not what answers”.

Open questions

  • A service account instead of yours? A dedicated account such as _omlx would keep the server, and any future tools, out of your home folder. It would need its own settings and the 126 GB of models moved to a folder it owns. That is the one case where a shared models folder comes back. It is not worth doing until MCP tools or more users arrive.
  • Should phil’s and nate’s devices reach it over the tailnet? Today the tailnet is yours alone. Letting their devices in means sharing this Mac with their tailnet accounts and restricting them to port 8000 in the access rules. The keys already work over that path.
  • Power settings: still yours to decide, as above.
